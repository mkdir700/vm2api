# 统一线上升级流程

状态：离线发布与独立执行器已实现。面板任务提交和协调升级尚未实现。

当前操作入口见 [本机发布与线上离线升级](offline-upgrade.md)。

## 目标和边界

面板和命令行应使用同一个升级执行器。
升级执行器应在控制平面停止后继续运行。
执行器复用现有 Docker Compose 和独立升级容器模式。
执行器不安装常驻升级服务。

线上只安装已构建、已验收的发布工件。
源码构建属于发布流程，不属于线上升级流程。
发布可以通过镜像仓库或离线导入交付。
两种交付方式应使用相同的身份校验和升级步骤。

本设计不改变 Hermit 的生产激活限制。
升级 vm2api 不会自动激活 Hermit。

## 当前差异

| 入口 | 当前行为 | 需要统一的部分 |
| --- | --- | --- |
| `deploy/install.sh upgrade` | 选择发布版本，更新部署文件，启动服务，再同步槽位 | 任务、预检、备份、切换、验收和回滚 |
| 面板升级 | 启动独立容器执行 `scripts/panel-upgrade.sh` | 同上 |
| 本次 primaryserver 部署 | 一次性 Python 脚本构建并验收完整镜像，再切换和回滚 | 只能作为迁移证据，不能继续作为独立生产入口 |

现有代码已经包含部分保护。
槽位同步已经按内容检测变化。
不能把调用整批同步接口等同于重启所有槽位。
本设计要求用同一个执行器组合这些保护。

## 发布工件

每次发布应提供以下信息：

- 发布版本、源码提交和目标架构。
- 交付镜像引用、仓库摘要或离线归档摘要。
- 加载后的镜像 ID，以及镜像中的源码标签。
- 部署文件、helper、槽位载荷和可选内核包的摘要。
- 支持的升级来源、数据库变更和回滚条件。
- 控制平面与现有槽位协议的兼容范围。
- 验收工件地址，以及被验收的全部工件摘要。

仓库摘要、离线归档摘要和本机镜像 ID 是不同的身份。
执行器应分别核对，不得互相替代。
摘要验证完整性，发布来源验证可信性。
执行器只接受配置的发布来源或明确导入的离线发布。
执行器不能因为某个文件存在就把发布标记为已验收。

发布流程负责完整功能验收。
线上执行器核对验收身份，并验证本机安装结果。
线上执行器不重复构建，也不重复运行完整模拟矩阵。
源码、镜像、内核包或用于验收这些工件的测试改变后，应重新完成相应验收。

## 升级任务

面板和命令行只创建、查询或取消升级任务。
两种入口不得各自维护升级步骤。
首次安装保留独立入口。
已有源码安装应先通过显式迁移进入镜像部署模式。
执行器不得根据 `.git` 的存在自动改为线上源码构建。

每个安装目录同时只允许一个升级任务修改状态。
任务记录应持久化到宿主安装目录。
任务记录至少包含任务 ID、原版本、目标身份、阶段、时间和结果。
页面关闭、SSH 断开或控制平面重启不能终止任务。
执行器自身退出后，新的执行器先核对实际状态，再决定恢复或回滚。
执行器不得只根据过期锁文件判断任务仍在运行。

任务结果应区分：升级成功、升级失败但已回滚、需要人工恢复。
接口返回任务已创建，不代表升级成功。
同一目标重复提交时，返回现有任务或核对当前状态。

## 标准步骤

### 1. 解析目标

解析明确版本或发布通道。
把目标固定为不可变发布身份。
保存原容器、镜像、Compose 项目、挂载和配置身份。
拒绝安装目录、架构、项目或容器身份不匹配的请求。

### 2. 准备工件

保持现有服务运行。
提前下载或导入镜像、槽位依赖和内核包。
核对摘要、磁盘空间、权限和部署文件。
保留管理员的 Compose 覆盖文件。
先在暂存目录验证目标部署配置，再修改活动文件。
不得把 `compose config` 中的密钥写入公开日志。

槽位基础镜像下载应在此阶段完成。
API 启动不能等待外部镜像仓库。
只更新控制平面时，不下载无关槽位镜像。

### 3. 本机预检

用目标镜像启动独立预检容器。
预检容器使用合成配置和独立数据目录。
预检容器不得挂载生产数据库、凭据或 Docker socket。
核对启动、`/health`、`/cc` 和页面资源。
核对数据库版本和回滚条件。
对无法安全回滚的迁移，执行器应在停机前给出明确处理方案。

### 4. 暂停调度并排空

保存升级前的槽位调度状态。
使用本次任务独有的暂停标识。
确认在途请求为零后，才允许切换。
超时后保持原版本运行，并撤销本次暂停。
不得强制结束请求，也不得自动重放请求。

### 5. 一致性备份

在服务运行期间，提前保存不可变文件和旧镜像。
在停止控制平面后，备份数据库、配置和可变状态。
核对数据库一致性，并保存备份摘要。
备份范围应包含本次切换会覆盖的持久化 helper 和部署文件。
按摘要保存不变的内核包和 CLI，不在停机阶段重复压缩。
预拷贝不能替代可变状态的一致性备份。
备份失败时，不切换目标版本。

### 6. 切换控制平面

原子更新镜像选择和必要的发布文件。
只重建本次任务指定的控制平面服务。
不得执行整个 Compose 项目的 `down`。
不得自动重建槽位、更新共享出口或修改反向代理。
核对实际镜像身份，不能只核对版本字符串。

### 7. 线上只读验收

保持本次调度暂停。
核对 API、管理页、资源、管理认证和数据库读取。
核对原健康槽位的内核状态。
核对槽位选择、凭据和出口绑定。
凭据摘要发生变化时，检查是否存在合法刷新，不得直接覆盖新令牌。
核对其他服务身份和状态。
常规升级不主动发送模型请求，也不执行 OAuth 刷新。
真实账号验收应作为单独的明确操作。

### 8. 恢复调度

只撤销本次任务创建的暂停。
保留管理员原有的暂停状态。
确认调度状态符合升级前记录，再写入成功收据。

### 9. 保留回滚材料

保留旧镜像、原部署配置、备份和本次收据。
清理只能删除超过保留策略的明确发布目录。
不得在成功后立即删除唯一可用的旧版本。

## 失败和回滚

切换前失败时，保留原服务并撤销本次暂停。
切换后、恢复调度前失败时，优先恢复原镜像和部署文件。
只有确认数据格式兼容后，才允许原版本使用当前数据。
需要恢复数据库时，先核对停机后的全部写入。
执行器不得自动覆盖已轮换的令牌或部署后产生的业务数据。

回滚后应重新验收，再恢复原调度状态。
回滚失败时，保留暂停并报告人工恢复所需的信息。
升级任务不能把回滚成功报告为升级成功。
恢复调度后的业务故障使用新的回滚任务处理，不直接恢复旧快照。

## 控制平面与槽位升级

控制平面升级默认保持槽位内核和 CLI 版本不变。
发布清单应证明该组合兼容。
若新控制平面要求槽位升级，预检应阻止单独升级。
执行器不能静默跳过必要的槽位变更。

槽位内核升级使用明确的槽位列表和固定版本。
槽位任务只处理变化的载荷。
每个槽位分别执行排空、切换、验收和回滚。
暂停调度前应说明现有会话和待返回工具结果的处理方式。
不能把所有内核的恢复能力视为相同。
需要协调升级时，先制定包含控制平面和槽位的完整任务计划。

Hermit 包安装、版本暂存和激活仍是三个不同操作。
普通重启不应用暂存版本。
统一线上升级流程不能绕过 Hermit 激活限制。

## 先写端到端验收

编码前覆盖以下失败方式：

- 面板和命令行执行不同步骤，或者重复任务同时切换。
- 发布身份、架构、安装目录或 Compose 覆盖文件不匹配。
- 下载中断、仓库不可用、磁盘不足或预检失败后原服务受影响。
- 在途请求未结束却停止服务，或者升级后重复执行工具。
- 备份不完整、数据库不一致、密钥泄漏或合法令牌刷新被覆盖。
- API 可用但管理页资源缺失，或者槽位协议不兼容。
- 控制平面退出导致执行器停止，或者执行器中断后无法恢复。
- 升级失败未回滚、回滚失败仍恢复调度，或者原暂停状态丢失。
- 控制平面升级意外重建槽位或共享出口。

使用独立 Docker daemon、实际 Compose 和实际镜像运行验收。
使用合成凭据、模拟上游和包含长请求的测试负载。
通过两个入口执行同一场景，并核对阶段和结果一致。
保留请求、工具执行次数、镜像身份、阶段耗时和清理收据。
发布升级能力时，应先通过这些验收。

## 实现顺序

1. 固定发布清单、任务状态和备份范围。
2. 先编写两个入口共用的端到端验收。
3. 实现独立升级执行器和命令行入口。
4. 让面板调用同一执行器，并展示阶段和耗时。
5. 移除旧入口中的重复执行逻辑。
6. 用标准流程升级 primaryserver，形成正式部署收据。

在第 6 步完成前，不把本设计称为已落地的生产升级流程。
